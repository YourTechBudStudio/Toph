# Mobile

## What this is

Toph's Expo React Native app for Android. iOS is not a target yet; do not configure or build it beyond what Expo generates by default.

## Tech stack

- Expo SDK 57 with the New Architecture, React Native 0.86 and React 19.2.3 (pinned).
- Expo Router with typed routes for routing and app composition.
- Zustand for shared or independently lived client state.
- React state for component-local concerns such as inputs, focus, and measured layout.
- Uniwind and Tailwind CSS v4 for styling. Tokens live in `global.css` and mirror the desktop palette.
- TypeScript is pinned to ~6.0 here because Expo tooling is not TypeScript 7 ready; the rest of the repo uses TypeScript 7.
- Tests run with `node --test`.

## Structure

Organize by capability so a feature's behavior can be understood locally.

```text
src/
  app/                      # Thin Expo Router routes and root composition
  modules/
    <capability>/
      index.ts              # Deliberate public interface
      components/           # Capability-specific UI
      state/                # Zustand state owned by this capability
  ui/                       # Shared components, layouts, and theme
plugins/                    # Expo config plugins applied at prebuild
tests/                      # node --test suites that are not owned by one module
```

## Native projects and builds

- `android/` and `ios/` are generated by `expo prebuild` (Continuous Native Generation) and are gitignored. Change native configuration through `app.json` or a config plugin in `plugins/`, never by editing generated folders.
- `plugins/dev-variant.ts` gives the Android debug build type a `.dev` application id and a "Toph Dev" label, so development and release builds install side by side. It also splits link schemes: debug builds answer `toph-dev://` and Expo's dev-client `exp+toph://`, and only the release build answers `toph://`, through a generated `src/release` manifest.
- `pnpm android` builds and launches the development build with the dev client. `pnpm release:android` builds and installs a release APK locally. There is no EAS.

## Rules

- Organize modules around capabilities, not necessarily individual screens. Keep related UI and state together.
- Expose narrow, meaningful interfaces through each module's `index.ts`. Cross-module consumers must not reach into private components or stores. Avoid chains of forwarding wrappers.
- Create internal files and directories only when they earn their place; the tree is not mandatory scaffolding for every module.
- Keep `app/` focused on routes, providers, and root composition. Product behavior belongs in modules.
- State ownership follows the capability responsible for its behavior, not the number of consumers. Resolve cross-capability coordination when concrete requirements arise.
- Use `ui/` for genuinely shared presentation. Reuse should prevent meaningful drift without turning shared UI into a home for unrelated product behavior.
- Colors and fonts come from tokens: a Tailwind class where one exists, `colors` from `ui/theme.ts` where a class cannot reach (SVG, icon colors, navigator options). `global.css` is the source of truth; no hex literals in screens.
- Until a story makes a capability real, its mock data and behavior live in that module's `state/`, behind the same public interface the real version will keep. Screens never hold mock data themselves.
- Never import React through a package shared with the desktop app. Mobile pins React 19.2.3 while `packages/desktop-ui` uses a newer React.
